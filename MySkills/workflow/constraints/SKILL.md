# Constraints 技能 — 专项约束接线与注册

## 定位

`constraints` 是工作流的**专项约束接线器**。

它负责把用户后续提供的行业规范、项目命名约定、模块规则、专项技能草稿或设计意图文档，转成一组可被工作流稳定匹配和装载的专项约束包。

它**不**负责：

- 直接实现业务代码
- 代替 `workflow/hr` 分配角色
- 代替 `parallel/*` 执行并行任务
- 让子智能体自行猜测该加载哪些专项规则

## 触发时机

- 用户输入 `/mywork-constraints`
- 用户提出“接入 Unity 规范”“接入项目命名约定”“把这些文档接到工作流里”
- 主智能体识别到仓库已有专项约束材料，但尚未注册到工作流

## 当前阶段说明

当前阶段先负责**注册与建档**：

- 建立专项约束目录与固定索引
- 把用户材料整理成约束包文档
- 明确适用范围、适用角色、文件范围与默认装载模式

后续是否自动装载、如何回显、如何进入并行/HR 协议，由主规则和相关技能接线决定。

## 固定入口

专项约束目录固定为：

```text
MySkills/project-constraints/
├── README.md               ← 固定索引文件（必须存在）
└── *.md                    ← 后续注册的专项约束包
```

即使用户尚未提供任何专项内容，`README.md` 也必须存在，用来表达“该层已启用，但当前为空”。

## 工作流程

### Step 1: 读取固定索引

先读取 `MySkills/project-constraints/README.md`，确认当前：

- 是否已有注册包
- 是否存在默认启用的专项约束
- 是否需要新增、更新或停用某个约束包

### Step 2: 收集用户材料

约束来源可以是：

- 行业规范文档（如 Unity 开发规范）
- 项目命名约定
- 模块规则或边界说明
- 技能草稿或专项实现约束
- 用户口述的偏好与限制

### Step 3: 整理成约束包

每个专项约束包至少应明确：

- 约束包名称
- 类型（行业 / 项目 / 命名 / 模块 / 其他）
- 适用任务
- 适用角色
- 适用文件范围
- 装载模式（默认 / 必须 / 可选）
- 来源材料

### Step 4: 更新固定索引

写入或更新 `MySkills/project-constraints/README.md`，确保主智能体后续能通过固定索引发现这些约束包。

### Step 5: 显式回报结果

完成后必须告诉用户：

- 新增或更新了哪些专项约束包
- 当前固定索引里有哪些包
- 哪些内容只是“已注册”，哪些已经进入工作流装载链路

## 禁止项

- 不得把专项约束和 agent 角色定义混在同一目录
- 不得假设子智能体会自行发现这些规则
- 不得在没有固定索引文件的情况下只创建空目录
- 不得把仍未注册的草稿文档直接宣称为“已接入工作流”
