# MyDocsSkill Iteration Log Policy

## 目标

把迭代日志的触发条件、写入时机和最小内容固定下来，避免 AI 在完成一个迭代后直接进入下一迭代。

`AGENTS.md` 负责任务分级与最终门禁；本文件只细化日志写法与写入时机。

## 何时必须写

- **每个迭代完成后都必须写一条迭代日志**（不论 S/M/L 级别）。
- Sprint 内的每个 Day 是独立迭代，各有独立日志。

## 写入时机

1. 当前迭代完成实现。
2. 当前迭代完成验证。
3. 在请求用户确认之前，先写迭代日志。
4. 用户确认后，才可以开始下一迭代。

## 写入位置

- 必须写入 `Docs/IterationLogs/`。
- 必须为每个已完成迭代新增一个独立日志文件。
- 不得只在 `Docs/Plans/`、`Docs/Current/` 或其他文档里补一句结果状态来替代迭代日志。
- 日志文件名必须带 `YYYY-MM-DD-` 年月日前缀，推荐使用 `YYYY-MM-DD-SprintN-迭代-主题.md`。

## 强制内容

每条迭代日志必须包含以下所有段落：

1. **日期** — 执行日期
2. **迭代目标** — 本轮交付什么
3. **执行内容** — 做了什么，每个任务一行
4. **验证结果** — 每项判定 [PASS]/[FAIL]，FAIL 附失败原因
5. **当前迭代 BUG** — 必填段落。本轮发现的所有 BUG，每条记录：
   - 编号（BUG-N）
   - 现象（观察到什么）
   - 根因（为什么发生）
   - 解决措施（怎么修的）
   - 状态（已修复 / 待修复 / 已记录延后）
   - 若本轮无 BUG，写"无"
6. **产出文件清单** — 本迭代新增或修改的文件列表
7. **下一步** — 等待确认 / 下一迭代目标

## 目录要求

- 若任务需要按迭代推进，应确保 `Docs/IterationLogs/` 可用。
- 如果项目还没有该目录，应在第一次需要写迭代日志前创建最小承载结构。
- 若目录刚创建，至少补一个 `README.md` 或模板说明，避免后续再次退回其他文档代写。

## 归档触发

满足以下任一条件时，日志将触发归档（具体规则以 `AGENTS.md §5.4` 为准）：

- 阶段切换（如 Sprint 0 → Sprint 1）：归档上阶段全部日志
- `Docs/IterationLogs/` 条目 ≥ 10：归档最早 5 条
- 关联计划全部迭代执行完毕：随计划一并归档

归档后的日志从 `Docs/IterationLogs/` 迁移到 `Docs/Archive/IterationLogs/`，并在 `Docs/Archive/IterationLogs/README.md` 索引中记录。

## 禁止项

- 不写日志就直接开始下一迭代。
- 跳过"当前迭代 BUG"段落（必须出现，无 BUG 写"无"）。
- 把多个迭代合并成一条笼统日志。
- 只写"已完成"而不写验证结果与影响范围。
- 只在计划文件里写"第几个迭代已执行"而不生成独立日志文件。
- 归档后不更新归档索引。
